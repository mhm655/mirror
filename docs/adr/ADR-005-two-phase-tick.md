# ADR-005 — Two-phase tick with a serial commit

**Status:** accepted · **Date:** 2026-08-30

## Context

The engine must run region workers in parallel without the result depending on
how many workers there are, or on the order the scheduler happens to run them
in.

## Decision

Every tick has two phases. Phase A runs in parallel, one goroutine per region,
and each region may write only its own owned entities and its own scratch
buffers. Phase B is serial: every region's intents are merged into one stream,
sorted by `(kind, primary id)`, and applied in that order.

## Reasoning

The alternative that looks obvious — let each region commit its own intents
directly, in region order — is the one that breaks determinism. Consider two
vehicles in different regions competing for the last free slot on a shared
link. Under per-region commit, whichever region happens to be processed first
wins. A run with four regions processes regions in a different relative order
than a run with one region, so the four-region run and the one-region run can
make different choices from identical starting state. "Distributed execution is
deterministic" would be a lie.

Merging into one global stream and sorting by `(kind, id)` before applying makes
the winner a function of vehicle id alone. That is identical at every partition
count, because the sort key never mentions which region an intent came from.

The two-phase split is what makes parallel phase A safe at all. Phase A reads
the whole network (a driver must see congestion outside its own region to route
around it) but writes only owned state. Nothing to reconcile, no fine-grained
locking, no atomics — the ownership discipline is the whole synchronisation
mechanism, and the race detector verifies it holds.

## Consequences

- Every structural mutation — allocating a vehicle, crossing an edge, admitting
  a patient — must go through an `Intent`, not a direct write, if it could be
  visible to more than the region that produced it. This is more ceremony than
  a direct write, and is the reason the codebase has an `Intent` enum with a
  documented per-kind payload.
- The serial commit is a hard ceiling on scaling (Amdahl's law). It is measured
  and reported by the benchmark harness rather than hidden — see the
  blueprint's performance section.
- Some intents are generated by the commit phase itself (an arriving transit
  vehicle puts its passengers onto a walking leg). The commit drains its own
  output in a second bounded pass so these are not silently lost — a bug this
  design initially had, caught by the repartitioning test.
